# Proposal — separate signal-volume changes from threat escalation in executive narratives

**Status:** PROPOSAL · 2026-05-29 · awaiting operator direction.
**Context:** PR #42 removed the methodology-injection contamination from `generate-executive-report` and was validated against the Trent Reznor report. Regenerated report `da726d61` cleared all 7 operator success criteria — *but* the narrative still says "ESCALATING" while the Flash says "STABLE" on the same report. This is a different failure mode.

---

## Three operator questions, answered

### Q1. Why does "4 signals this week vs 0 last week" become "escalating threat activity"?

A pattern-detector signal lands in the database with these fields:

| Field | Value |
|---|---|
| `title` | `[PATTERN] Frequency spike: 4 signals this week (0 prior week)` |
| `normalized_text` | `Signal frequency spike: 4 signals this week vs 0 last week.` |
| `severity` | `medium` |
| `signal_type` | `pattern` |
| `category` | **`active_threat`** ← the structural promotion |
| `source_url` | NULL (internal detector, no external observation) |

The function `generate-executive-report` then walks this signal through:

1. `EXCLUDE_CATEGORIES` filter (line 283) — `active_threat` is not in it, signal passes.
2. `HIGH_VALUE_CATEGORIES.has(s.category) && s.severity === 'low'` (line 287) — signal is medium, not low, signal passes.
3. `signalsByCategory` (line 300) — grouped under `active_threat`.
4. `weightedCategories` (line 845) — medium severity contributes +1 each. Three identical pattern signals = score 3. **Just passes the `score >= 3` threshold.** Category selected for narrative.
5. `narrativesPromises` (line 859) — builds the narrative prompt for the `active_threat` category, displayed to the LLM as "**Active Threat threats** for ${client.name}."
6. The prompt presents the signals as: `1. [MEDIUM] Signal frequency spike: 4 signals this week vs 0 last week.` (× 3, identical).
7. The MANDATORY TRADECRAFT RULES say: *"State the trajectory for this threat category: ESCALATING, STABLE, or DE-ESCALATING vs last period."* The LLM is required to pick one.

The LLM is given:
- A category label that says *"Active Threat"*.
- Three identical inputs that literally say *"spike: 4 vs 0"*.
- An instruction that says *write a threat narrative*.
- A required-output schema with `{ESCALATING, STABLE, DE-ESCALATING}`.

Of the three trajectory choices, **ESCALATING is the only one consistent with the input's surface text** ("spike", "4 vs 0"). The LLM doesn't see — and the prompt doesn't tell it — that pattern signals are meta-observations about signal flow, not external threat observations. So it picks ESCALATING and writes a threat narrative around that conclusion.

The root cause is the **category-label promotion**: pattern signals get tagged `category: active_threat` at ingest time, which means they survive every downstream filter that's intended to gate threat narrative.

### Q2. Why does the narrative override the Executive Flash assessment?

Two completely separate code paths produce them.

The **Executive Flash** has a deterministic short-circuit (line ~530):

```ts
const isQuietPeriod =
  criticalSignals.length === 0
  && highSignals.length === 0
  && newIncidentsLast24h.length === 0
  && (overallRiskLevel || '').toUpperCase() === 'LOW';
```

When this is true, the Flash skips the LLM entirely and emits deterministic text: `"No critical or high-severity signals…3 lower-severity signals…no escalation indicators." / "No immediate action required."` The Flash *cannot* hallucinate trajectory in a quiet period.

The **Narrative section has no equivalent gate.** It runs the LLM unconditionally whenever any category has weighted score ≥ 3 — and 3 medium pattern signals hit that threshold exactly. There is no consistency check that compares narrative output against Flash output. There is no precedence rule. Both sections write to top-level keys on `meta_json` and ship in the same report.

The narrative doesn't *override* the Flash — they're independent oracles that happened to disagree. The Flash spoke the truth (LLM was bypassed); the narrative spoke the LLM's interpretation of the same data.

### Q3. Which section should be authoritative when risk = LOW and trajectory = STABLE?

**The Executive Flash, unambiguously.** Three reasons:

1. **Determinism.** When `isQuietPeriod` is true, the Flash text is generated by a switch statement, not by an LLM. It cannot hallucinate trajectory. The Narrative can and does.
2. **Computation grounding.** Flash trajectory is derived from raw integer counts (`criticalSignals.length`, `highSignals.length`, `newIncidentsLast24h.length`, `overallRiskLevel`). Narrative trajectory is LLM-inferred from category-grouped natural-language signal text. The Flash is *measured*; the Narrative is *interpreted*.
3. **Reader role.** Executives read the Flash first. The Flash is the contract. The Narrative is supposed to be the *evidence backing* the Flash, not a parallel oracle. If the Flash says LOW/STABLE/no-action and any other section disagrees, the disagreeing section is the bug.

This authority hierarchy should be made explicit in the function: **every other section must be consistent with the Flash**. The Narrative is currently allowed to contradict it. That is the structural defect.

## Three approaches evaluated

| # | Approach | Pros | Cons | Failure mode that survives |
|---|---|---|---|---|
| **1** | **Narrative quiet-period gating.** Replicate the Flash's `isQuietPeriod` short-circuit on the narrative pipeline. When triggered, emit a deterministic per-category narrative consistent with the Flash. | Simple. Identical pattern to existing Flash logic. Single source of truth for "is this period quiet." Eliminates LLM freedom to invent narrative trajectory when nothing is happening. | Coarse — fires only when *every* condition is quiet (`0 critical + 0 high + 0 new + LOW`). | If a future period has 1 high signal + 3 medium pattern signals, `isQuietPeriod` is false, gate doesn't fire, pattern signals can still be promoted to ESCALATING narrative voice by the same path as today. |
| **2** | **Exclude `signal_type='pattern'` from narrative input only.** Add `narrativeSignals = reportableSignals.filter(s => s.signal_type !== 'pattern')`. Pattern signals still appear in Flash counts, Signal History, and Evidence Sources — they only disappear from the narrative LLM's input. | Directly removes the contamination source. Pattern signals never reach the narrative LLM. Narrative trajectory only reflects external-observation signals. Clean separation between *signal-flow meta-metrics* and *threat observations*. | Pattern signals are real information. They should still appear in Signal History (they do, this preserves it). Implementation must be precise — careless filtering at `reportableSignals` would also affect Flash counts. | If a future signal type is also a meta-observation but isn't labeled `signal_type='pattern'`, the filter misses it. The fix is per-signal-type granular; not category-based. |
| **3** | **Explicit signal-volume labeling in the prompt.** When a pattern signal reaches the narrative prompt, prefix it: `[INTERNAL PATTERN OBSERVATION — signal-volume meta-metric, not a threat observation]`. Add a hard prompt directive: *"Pattern-observation signals describe internal signal-flow metrics, not real-world threats. Never use them as evidence of escalating threat activity. They may be referenced as 'signal volume increased' but never as 'threats are escalating'."* | Keeps pattern signals visible to the LLM (preserves the rare case where a frequency spike IS worth narrating, e.g. as an explicit signal-flow observation). Teaches the model the distinction. Cheapest implementation. | **Relies on the LLM honoring the label.** Prompt discipline in this codebase has a track record of drift — the methodology-injection case is the most recent example (the prompt already said "ground in signals only" and the LLM still lifted methodology). Less robust than structural exclusion. | The LLM ignores the label and writes escalation language anyway. Less deterministic than #1 or #2. |

## Recommendation: **2 + 1**, defense-in-depth

Adopt **Approach 2 as primary, Approach 1 as backstop. Do not adopt Approach 3 alone.**

**Primary — structural exclusion (Approach 2).** Pattern signals are meta-observations about signal flow, not threat observations. They should never seed a threat narrative. Implement as:

```ts
// Pattern-detector signals describe signal-flow meta-metrics, not external threat
// observations. They remain in Flash counts and Signal History (for operator drill-down),
// but they do not feed the narrative LLM. This is the structural enforcement of
// "signal increase ≠ threat increase" per operator directive 2026-05-29.
const narrativeSignals = reportableSignals.filter((s: any) => s.signal_type !== 'pattern');
```

Then build `signalsByCategory` and `weightedCategories` from `narrativeSignals` instead of `reportableSignals`. Flash and Signal History sections continue to use `reportableSignals` unchanged.

**Backstop — extend `isQuietPeriod` to the narrative section (Approach 1).** Even after pattern signals are excluded, if the remaining narrative-input set has no critical, no high, no new incidents, and overall risk = LOW, the narrative LLM should not run. Emit deterministic per-category text consistent with the Flash:

```ts
const isNarrativeQuietPeriod =
  narrativeSignals.filter((s: any) => s.severity === 'critical').length === 0
  && narrativeSignals.filter((s: any) => s.severity === 'high').length === 0
  && newIncidentsLast24h.length === 0
  && (overallRiskLevel || '').toUpperCase() === 'LOW';

if (isNarrativeQuietPeriod) {
  // Deterministic narrative; no LLM call.
  return weightedCategories.map(({ category }) => ({
    category,
    narrative: `No significant ${getCategoryDisplay(category).toLowerCase()} activity detected in the reporting period. See Signal History below for detail on lower-severity items.`,
    signals: [],
  }));
}
```

**Why not Approach 3 alone:** prompt-only discipline has failed repeatedly in this codebase. The methodology-injection case proved that "ground in signals only" instructions are not sufficient when the prompt also gives the LLM material it can lift. The cheapest patch is the most fragile; structural exclusion is the durable fix.

**Optional addition from Approach 3:** if the operator wants belt-and-braces, *also* add the explicit prompt label inside the narrative prompt for any pattern signal that somehow leaks through (defense in depth, not primary defense). This costs ~50 tokens per pattern signal — acceptable.

## What this proposal does **not** do

- Does not touch the methodology-injection path (already fixed in PR #42).
- Does not address the wider sweep of report-generation functions (`generate-daily-briefing`, `generate-consortium-briefing`, `generate-poi-report`) for the same Narrative-vs-Flash inconsistency. Those are likely affected but should be evaluated separately per the operator's stated "do not widen sweep yet."
- Does not touch the Impact Ladders or Deductions sections. Those have separate generation paths and separate ground-truth gates today.
- Does not propose changes to the pattern detector itself (e.g. why pattern signals are tagged `category: active_threat` at ingest). That is a more invasive change with broader downstream effects.
